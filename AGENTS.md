# GRIDLINE — repository notes

Hungarian-language **motorsport community platform** (the project was rebranded from its original car-parts-only name).
Next.js (App Router) + TypeScript + Tailwind CSS. Two modules live side by side:

- **Motorsport**: Hungarian circuit database (`tracks` / `track_layouts`),
  lap-time leaderboards (`lap_times`), manual + GPS lap submission, driver
  profiles, community feed. Slogan: *"Find your line. Set your time."*
- **Parts compatibility** (retained): vehicle catalog, parts search,
  compatibility checker, garage.

**Database-backed**: everything comes from a **Supabase (PostgreSQL)** database.
There is no built-in demo/mock data and no fabricated fallback — when the DB is
unreachable the UI shows a clear error, never invented content. No external AI
service.

## Commands

- `npm run dev` — dev server
- `npm run build` — production build (runs ESLint + type check; all routes must be static)
- `npm run start` — serve the production build
- `npx tsc --noEmit` — fast type check
- `node scripts/verify-supabase.mjs` — read-only Supabase connectivity/table check (needs `.env.local`)

## Architecture

- `src/lib/` — logic: `types.ts` (domain types mirroring the DB schema),
  `status.ts` (`STATUS_META` for compatible/incompatible/uncertain),
  `compatibility-db.ts` (the only compatibility engine), `part-images.ts`,
  `shop-links.ts`, `api.ts` (client fetch helper), `utils.ts`. `cars.ts` holds
  small static helpers only (no demo catalog).
- `src/lib/catalog/CatalogProvider.tsx` — **DB-backed catalog**. Exposes
  `ready`, `status` (`loading` / `ready` / `unavailable`), `source`
  (`"database" | "none"`), `dbAvailable`, `message`, `brands`, `categories`,
  `parts`, `ensureModels(brandId)`, `ensureEngines(brandId, generationId)`
  (lazy, idempotent), `getMake/getModel/getGeneration/getEngine/getPart`,
  `isLoadingModels`/`isLoadingEngines`, async `searchParts(term)` and
  `refresh()`. Loads brands/parts/categories on mount; when Supabase is
  unconfigured or unreachable it sets `status: "unavailable"` and empty lists —
  it does NOT fall back to demo data.
- `src/lib/supabase/` — `config.ts` (env detection), `client.ts` (memoized
  browser client), `server.ts` (`getAuthContext`/`getAdminClient`/`isServerConfigured`
  for API routes, Bearer token → service_role), `queries.ts` (typed selects,
  `normalizeOeNumber`), `mappers.ts` (DB rows → UI types, incl. `mapPart`,
  `mapProfile`, `firstEmbedded`).
- `src/lib/compatibility-db.ts` — `runDatabaseCompatibilityCheck(input)`.
  Resolves the part by OE number → manufacturer SKU → name, then reads the
  `fitments` table. Returns `null` when Supabase is unavailable (the caller shows
  an error). No match / no fitment / out-of-range year ⇒ `uncertain`, never
  `compatible`.
- `src/context/AppContext.tsx` — single state provider (auth session, garage,
  favorites, saved checks, search log). Consumes `useCatalog()`; exposes
  `catalogParts`, `allParts`, `findPart(id)`, `register`/`login`/`logout`
  (Supabase Auth), and DB-backed mutators. Wraps everything in `layout.tsx`,
  nested inside `CatalogProvider`.
- `src/components/` — shared UI (`ui.tsx` incl. `DbNotice`, `Navbar`, `Footer`,
  `Toaster`, `Logo`, `CarSelector`, `PartCard`, `PartImage`, `PartDetailModal`,
  `PartDetailContent`, `ShopLinks`, `CompatibleCars` (reads DB `fitments`),
  `RelatedParts`, `ResultCard`, `AuthForm`).
- `src/app/api/` — server routes (see README): user data (`garage`, `checks`,
  `favorites`, `search-history`, `me`) and admin (`admin/parts`,
  `admin/users`, `admin/stats`, `admin/import`). All use the service_role key
  server-side and verify the caller's Supabase session/role.
- `src/app/admin/` — admin dashboard with its own `layout.tsx` + `AdminShell`
  guard (`AdminLogin` when not admin). Parts CRUD, users list, statistics.
- `src/app/alkatreszek/[id]/` — dedicated part detail page.
- `src/lib/part-images.ts` — `partImage(part)` resolves a part to its product
  `image_url`, else a category/keyword SVG in `public/parts/`.
- `src/lib/shop-links.ts` — builds webshop search links (eBay, Ovoko, Allegro,
  Autodoc, Trodo) from the part's OE/SKU.
- `public/parts/*.svg` — 34 self-contained part illustrations, generated by
  `scripts/gen_part_images.py`.
- `scripts/make_zip.py` — rebuilds `public/gridline.zip` for the `/letoltes`
  page. **Re-run after adding/removing source files.**

## Conventions

- Route folder names are Hungarian: `kompatibilitas`, `alkatreszek`, `garazs`,
  `fiok`, `bejelentkezes`, `regisztracio`, `utitervek`, `rolunk`, `kapcsolat`,
  `letoltes`, `admin/{alkatreszek,felhasznalok,statisztikak}`.
- Every page has Hungarian `metadata`; UI copy is Hungarian.
- No "demo" wording anywhere. Data shown is real DB data; when the DB is
  unavailable the UI must show an error/notice (`DbNotice` is the emerald
  "real database" note), never placeholder content.
- Public components read the catalog via `useCatalog()` / `useApp().allParts`
  rather than importing static catalog constants.
- Compatibility is decided ONLY by `fitments`; extend
  `src/lib/compatibility-db.ts` (return type `CompatibilityResult` stays stable).

## Gotchas

- Supabase is required. Only the public anon/publishable key belongs in the
  client (`NEXT_PUBLIC_*`); the `service_role` key is server-side only. Copy
  `.env.example` → `.env.local`.
- The `/kompatibilitas` URL prefill (from the homepage QuickCheck) calls
  `ensureModels`/`ensureEngines` on mount; the DB generation id equals
  `vehicle_models.id`. `CatalogProvider` keeps `modelsByBrand`/`enginesByModel`
  caches and re-applies them in the initial brand load (`applyCachedModels`) so
  the initial fetch cannot clobber lazily-loaded models/engines.
- **Garage `model_id` mapping**: in the UI the "Modell" dropdown is a synthetic
  group id (`${brandId}-${slug}`), while the DB `vehicle_models.id` is the real
  model/generation id (e.g. `golf-7`). The client sends both `modelId` (group)
  and `generationId` (real id). Server-side `toRow` in `api/garage/route.ts`
  MUST store `generationId` into `user_vehicles.model_id` (the FK), otherwise the
  insert fails with `user_vehicles_model_id_fkey`. When loading a car into the
  edit form, resolve the group id from the generation id (search each model's
  `generations`), not from `car.modelId`.
- `next lint` has no ESLint config and prompts interactively; rely on
  `npm run build` for lint+type validation instead.
- After editing a client component, re-run `npm run build` **and restart
  `next start`** — the production server keeps serving the previously-built
  chunks otherwise (kill the stale `next-server` process; check `ps`).
- The downloadable archive at `/letoltes` is served from `public/gridline.zip`
  through the `/api/download/gridline` route (that route sets
  `Content-Disposition: attachment`; the `download` HTML attribute alone is not
  reliable in embedded/headless views). Regenerate the ZIP with
  `python3 scripts/make_zip.py` after source changes, then **rebuild** — the page
  reads size, file count and SHA-256 at build time, so a stale build advertises a
  checksum that no longer matches the file.
  The ZIP is **committed to the repo** (so it ships with the deploy), which
  means it must be regenerated and re-committed whenever sources change —
  otherwise `/letoltes` serves a stale archive. `make_zip.py` excludes itself
  from the archive and writes `gridline/` as the top-level folder.

### The second download: the offline website snapshot

`/letoltes` offers **two** packages:

| File | What it is | Route |
| --- | --- | --- |
| `public/gridline-weboldal.zip` | the running site as a static snapshot (24 pages) | `/api/download/weboldal` |
| `public/gridline.zip` | the full source code | `/api/download/gridline` |

Build both with `./scripts/package_all.sh` (it runs `snapshot_site.py`,
zips `public/site/`, then runs `make_zip.py`). The snapshot is taken from the
**running** server, so start it first (`./scripts/start-public.sh`).

`scripts/snapshot_site.py` drives headless Chromium over CDP and saves the
rendered DOM per route — plain HTTP fetching is not enough, because the track
list, leaderboards and parts grid are client-rendered from Supabase.

Three details that are easy to get wrong:

- **Scripts are stripped on purpose.** Offline there is no Supabase, so React
  hydration would replace the captured content with an error state.
- **CSS font URLs must be rewritten.** The exported CSS references
  `/_next/static/media/*.woff2`; under `file://` an absolute path does not
  resolve, so the snapshot silently falls back to system fonts (the homepage
  wordmark renders 886 px wide instead of 621 px). `snapshot_site.py` rewrites
  `url(/_next/` to a relative path *after* copying the assets, and copies the
  19 font files from `.next/static/media/`.
- **The page reads ZIP metadata at build time** (size, file count, SHA-256), so
  the order is: build → `package_all.sh` → build again. Otherwise `/letoltes`
  advertises the previous file count.

## Local test harness (Supabase-compatible)

The dev sandbox runs a local Supabase-compatible stack behind the port-12001
proxy (`/workspace/dbtest/supabase_proxy.py` → PostgREST `:13000` + GoTrue
`:13001`):

- PostgREST `gridline-rest` (v12) and GoTrue `gridline-auth` (v2.151) containers
  share the `gridline-db` Postgres container; GoTrue needs
  `GOTRUE_JWT_DEFAULT_GROUP_NAME=authenticated` **and** `auth.users.role =
  'authenticated'` — otherwise it mints tokens with an empty `role` claim and
  PostgREST rejects every authenticated request with
  `role "" does not exist` (HTTP 400).
- Seed SQL lives in `/workspace/dbtest/` (`schema.sql`, `parts_seed.sql`,
  `profiles.sql`, plus the `build_*_seed.py` generators).
- **The stack is not running after a sandbox restart.** Bring it up with
  `sudo dockerd &` (the daemon is not started automatically), then
  `sudo bash /workspace/dbtest/start_stack.sh` and
  `sudo bash /workspace/dbtest/apply_migrations.sh`, then
  `nohup python3 /workspace/dbtest/supabase_proxy.py &` (listens on `:12001`).
  `apply_migrations.sh` is not fully idempotent — it aborts on the
  `policy "user_licences_owner_read" ... already exists` error; that is
  harmless, the tables are already created.
- **The work-1 proxy (`https://work-1-…`) forwards to `localhost:12000`, NOT
  `3000`.** Start the dev server with `npx next dev -p 12000` (the `npm run dev`
  script hardcodes `-p 3000`, which the proxy cannot reach → HTTP 502). Check
  the port with `/proc/net/tcp`: a listener on `12000` must be present.
- **Sandbox secrets override `.env.local`.** The runtime injects
  `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` pointing at the
  *real* Supabase project, and `process.env` wins over `.env.local` in Next.js.
  The real project has no `tracks` table (migrations unapplied) and its JWT
  secret differs from the local stack, so authenticated REST calls fail with
  `403 JWSInvalidSignature` and pages show `PGRST205 Could not find the table`.
  To test against the local stack, launch dev with the local values explicitly,
  e.g. `source /workspace/dbtest/.stack.env && env NEXT_PUBLIC_SUPABASE_URL=https://work-2-… \
  NEXT_PUBLIC_SUPABASE_ANON_KEY="$PGRST_ANON_KEY" SUPABASE_SERVICE_ROLE_KEY="$PGRST_SERVICE_KEY" \
  npx next dev -p 12000`. Confirm the baked URL by grepping the client chunks
  (`/_next/static/chunks/app/layout.js`) for `work-2-` vs `supabase.co`.
- **Never run `npm run build` while `next dev` is running** — the build
  overwrites `.next` and the dev server then throws `Cannot find module
  './NNNN.js'`. Restart dev with a clean `.next` afterwards.
- **Production serve on the public host:** `./scripts/start-public.sh` exports
  the `.env.local` values (overriding the injected sandbox secrets) and runs
  `next start -p 12000`. A production `npm run build` must be run with the same
  explicit env, otherwise the `NEXT_PUBLIC_*` values are baked into the client
  chunks from the injected secrets and every page shows `PGRST205`. Verify with
  the chunk grep above after building.
- `public/tracks/*.{jpg,svg,png}` are the track hero/layout images referenced by
  `tracks.image_url` / `layout_image_url` in migration `0004_seed_tracks.sql`.

## Motorsport feature (tracks / lap times)

- Migrations `supabase/migrations/000{1..6}_*.sql` are idempotent; apply with
  `/workspace/dbtest/apply_migrations.sh`. They add `tracks`, `track_layouts`,
  `lap_times`, `gps_sessions`, `gps_laps`, `gps_samples`, `vehicle_categories`,
  `licence_levels`, `user_licences`, `follows`, `posts`, `track_favorites`.
- **Sequence grants (migration `0006`).** `gps_samples.id` is `bigserial`, so
  inserting samples needs `USAGE` on `gps_samples_id_seq`. Supabase grants this
  to the API roles by default; a plain Postgres (self-hosted/self-built) does
  not, and the GPS finalize `PATCH /api/gps-sessions` then fails with
  `permission denied for sequence gps_samples_id_seq`. `0006` grants
  `usage, select` on all `public` sequences (and default privileges for future
  ones) to `service_role`/`authenticated`/`anon`. Prefer `uuid … default
  gen_random_uuid()` for new tables to avoid the issue entirely.
- `lap_times` columns: `vehicle_label`, `vehicle_category`, `lap_time_ms`,
  `measurement_type`, `status`. The client sends `lapTime` as `"1:23.456"`;
  `normalizeLapPayload` (`src/lib/motorsport/lap-payload.ts`) converts to
  `lap_time_ms`. Every submission is forced to `status: 'pending'`.
- Leaderboards show **only** `status = 'approved'` rows; the RLS policy
  `lap_times_public_read` enforces `status = 'approved' or user_id = auth.uid()
  or is_admin()`.
- Admin review: `/admin/eredmenyek` → `PATCH /api/admin/lap-times`
  (`{ id, status: 'approved' | 'rejected', note }`). GPS results are never
  auto-trusted — they land as `pending` like manual ones.
- Navbar order follows the spec: Kezdőlap, Versenypályák, Ranglisták,
  Közösség, Garázs, Alkatrészkereső, then the **Fejlődés** dropdown
  (Fejlődési rendszer, Licencrendszer, Feladatok, Pontok, Fejlődésem) plus the
  current licence badge. `/licencek` still 404s — the licence content lives
  under `/fejlodes/*`.

## Progression system (licences / challenges / points)

Migration `0007_progression_system.sql` (schema) + `0008_challenge_pool.sql`
(extra badges). Both are idempotent.

- Tables: `challenge_definitions` (code, name, description, icon, points,
  category, `criteria` jsonb, sort_order, is_active), `user_challenges`
  (pk `user_id, challenge_code`), `points_ledger` (append-only; unique
  `(user_id, source_ref)` where `source = 'challenge'`), plus
  `licence_levels.min_points` and `user_licences`.
- **Points are server-only.** `claim_challenge(p_user, p_code)` is
  `SECURITY DEFINER` and `EXECUTE` is granted to `service_role` alone, so the
  client cannot mint points. `POST /api/progression` resolves `p_user` from the
  verified session and calls it; `get_progression(p_user)` builds the payload
  (challenges + summary + ledger) for `GET /api/progression`.
- `challenge_metric(p_user, criteria)` evaluates the real data. Supported
  `kind`s: `approved_laps`, `gps_laps`, `distinct_tracks`, `lap_under_ms`
  (needs `track_slug` + `target_ms`), `max_speed_kmh`. Unknown kinds return 0.
- 13 active badges total **3450 points**, so the top tier (A = 2000) is
  reachable. Thresholds (`licence_levels.min_points`) are Rookie 0, D 300,
  C 700, B 1200, A 2000 — provisional, kept in one place.
- `recompute_licence(p_user)` sums the ledger and sets `user_licences`;
  `trg_profiles_licence` seeds a rookie row for every new profile.
- UI: `src/lib/progression/ProgressionProvider.tsx` (client context),
  `src/components/progression/{ChallengeBadge,ChallengesContent,LicenceSystemContent,PointsContent,MyProgressionContent,LicenceBadge}.tsx`,
  pages under `src/app/fejlodes/{feladatok,licencrendszer,pontok,fejlodesem}`.
- Badge labels wrap (no `truncate`) so longer Hungarian names stay readable.

## Schema drift: `parts` / `part_oe_numbers`

The live Supabase DB no longer has these columns, but `/workspace/dbtest/schema.sql`
still declares them — the local test schema is stale:

- `parts`: removed `side`, `position`, `source`, `verified` (live has
  `created_at` **and** `updated_at`).
- `part_oe_numbers`: removed `source`, `verified`.

Selecting a removed column returns PostgREST `42703 column … does not exist`;
inserting one returns `PGRST204 Could not find the '…' column …`. The canonical
`parts` select is `PART_COLUMNS` in `src/lib/supabase/queries.ts`:
`id, category_id, name, manufacturer, manufacturer_part_number, description,
image_url, created_at`. Keep `mappers.ts` (`PartRow`), `types.ts` (`Part`),
`api/admin/parts/route.ts` (`buildPartRow`/`replaceOeNumbers`), `PartCard`,
`PartDetailContent` and `admin/alkatreszek/AdminParts.tsx` in sync. Note
`fitments` and `compatibility_reports` DO still have `source`/`verified` — only
`parts`/`part_oe_numbers` lost them.

## GRIDLINE rebrand notes (post-AutoFit)

- Brand is now **GRIDLINE**; slogan "Find your line. Set your time." lives in the
  footer + metadata only, never in the hero. `FooterGate.tsx` hides the footer on
  `/` exactly.
- Design language: flat `rounded-sm` surfaces, no `shadow-card`, no gradients in
  cards. `shadow-card` was a custom token and has been removed everywhere — do not
  reintroduce it.
- **Env-at-build gotcha:** `NEXT_PUBLIC_*` are inlined at build time. The sandbox
  injects a bogus 46-char anon key, so always build with `./scripts/build-public.sh`
  (and run with `./scripts/start-public.sh`); plain `next build` yields
  "Invalid API key" in the browser.
- Download archive is `public/gridline.zip` (regenerate with
  `python3 scripts/make_zip.py`).
- Lap flow: POST `/api/lap-times` → `status: pending`; admin approval is
  `PATCH /api/admin/lap-times` with `{ id, status, reviewNote }` in the **body**
  (there is no `[id]` sub-route). RLS hides pending rows from anon, so a lap only
  reaches `/ranglistak` after approval.

## Ranglisták felosztása (fontos!)

- **`/ranglistak` = PONTverseny** (`PointsLeaderboard.tsx` + `/api/leaderboard/points`):
  ki hány pontot gyűjtött. A pontok a `points_ledger` napló összege (ugyanaz, amit
  a `recompute_licence` használ). Mivel a `points_ledger`/`user_licences` RLS-sel
  védett, az összesítés **csak service_role-lal, szerveroldalon** készülhet — ezért
  van rá API route, nem közvetlen kliens-lekérdezés. A válasz csak nyilvános adatot
  ad (név, avatar-szín, pont, licenc) — e-mail és user_id SOHA.
- **Köridős ranglisták = a pálya adatlapján** (`/versenypalyak/[slug]`,
  `TrackDetail.tsx`), pályaváltozat + kategória + mérési mód szűrővel. Csak
  `status = approved` eredmények.
- A régi önálló `Leaderboards.tsx` (globális köridő-ranglista) **törölve** — ne
  hozd vissza, a köridők helye a pálya adatlap.

## Sandbox újraindulás után — stack indítási sorrend

A sandbox újraindulásakor a Docker daemon ÉS a DB stack is leáll, ilyenkor minden
adatot adó oldal „Bad Gateway"-t ad (a HTML-váz betölt, az adat nem). Sorrend:

```bash
sudo -n nohup dockerd > /tmp/dockerd.log 2>&1 &   # root kell, sima dockerd elhal
sleep 15 && sudo -n chmod 666 /var/run/docker.sock  # különben permission denied
cd /workspace/dbtest && ./start_stack.sh          # gridline-db/rest/auth
nohup python3 supabase_proxy.py > /tmp/proxy.log 2>&1 &   # :12001 → :13000/:13001
cd /workspace/project/penge && nohup ./scripts/start-public.sh > /tmp/next-12000.log 2>&1 &
```

Ellenőrzés: `curl localhost:12000/api/leaderboard/points` – valós JSON kell, nem
`{"error":"Bad Gateway"}`. A `pgdata` kötet megmarad, az adatok (profilok, pályák,
köridők, pontok) újraindítás után is megvannak.
